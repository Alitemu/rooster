# Dienstrooster - Phase 3: Assignment Viewing, Editing & Publication

## Context

Phase 1 provided preference collection. Phase 2 generated fair rosters using CP-SAT solver. Phase 3 adds the assignment viewing interface, manual editing capabilities, swap request workflow, roster publication, and staff notifications.

**Output:** After Phase 3, planners can review generated assignments, make manual adjustments, allow staff to request swaps, and publish the final roster with notifications sent to all staff.

## Architecture Overview

```
Phase 2 Output: assignments (generated by solver)
                ↓
Phase 3 Planner UI:
  - View assignments by person/day
  - Manual edit (drag-drop or inline edit)
  - Undo/redo capability
  - Swap management (approve/reject)
  - Publication workflow
                ↓
Phase 3 Staff UI:
  - View personal roster
  - Request shift swaps
  - Track swap requests
  - Notification inbox
```

## Data Model Additions

### New Tables

**dienstrooster_swap_request**
```sql
id (UUID primary key)
period_id (foreign key → schedule_period)
requester_id (foreign key → person)
offered_slot_id (foreign key → shift_slot)   # Slot requester wants to give away
requested_slot_id (foreign key → shift_slot)  # Slot requester wants to receive
respondent_id (foreign key → person)          # Who has the requested slot
status (enum: PENDING, APPROVED, REJECTED, REVOKED)
created_at (ISO timestamp)
responded_at (ISO timestamp, nullable)
resolved_by_person_id (nullable)              # Who approved/rejected
notes (text)
row_version (optimistic locking)
```

**dienstrooster_notification**
```sql
id (UUID)
person_id (foreign key → person)
period_id (foreign key → schedule_period, nullable)
type (enum: ROSTER_READY, ASSIGNMENT_MADE, SWAP_REQUESTED, SWAP_APPROVED, PUBLICATION_NOTICE)
subject (text)
body (markdown)
read (boolean, default false)
created_at (ISO timestamp)
dismissed_at (ISO timestamp, nullable)
```

**dienstrooster_assignment_edit**
```sql
id (UUID)
assignment_id (foreign key → assignment)
period_id (foreign key → schedule_period)
person_id (from assignment at time of edit
changed_from_person_id (if swap) or null (if new)
changed_to_person_id (if swap) or null (if deleted)
slot_id (from assignment)
edit_type (enum: MANUAL_ASSIGN, MANUAL_REMOVE, SWAP, OVERRIDE)
reason (text, nullable)
edited_by_person_id (foreign key → person, who made the edit)
row_version (int)
aangemaakt_op (ISO timestamp)
```

## API Routes (Phase 3)

### Assignment Viewing & Management

**Planner Routes:**
```
GET  /api/planner/period/[id]/assignments
     - List all assignments for period (with person details)
     - Filter by: person, shift_type, date range
     - Pagination: 50 per page
     - Response: { success, data: { assignments, total, people } }

GET  /api/planner/period/[id]/assignments/[person-id]
     - Single person's roster (all assignments)
     - Response: { success, data: { person, assignments, slot_details } }

POST /api/planner/period/[id]/assignments/manual-assign
     - Manually assign person to slot
     - Body: { person_id, slot_id, reason? }
     - Validates: no conflicts, respects blocking prefs, band limits
     - Response: { success, data: { assignment, diagnostics } }

DELETE /api/planner/period/[id]/assignments/[assignment-id]
     - Remove assignment (undo)
     - Body: { reason? }
     - Creates audit log entry
     - Response: { success }

POST /api/planner/period/[id]/assignments/swap
     - Swap two assignments (person A ↔ person B on same slot)
     - Body: { person_a_id, person_b_id, slot_id, reason? }
     - Validates: both have assignments on same slot
     - Response: { success, data: { assignments } }

GET  /api/planner/period/[id]/publication-check
     - Pre-publication validation
     - Checks: all slots filled, no hard blocking violations, band compliance
     - Response: { success, data: { valid, issues: [] } }

POST /api/planner/period/[id]/publish
     - Mark period as PUBLISHED, sends notifications
     - Body: { published_by_person_id }
     - Creates audit log
     - Sends notifications to all staff
     - Response: { success, data: { period, notifications_sent } }
```

**Staff Routes:**
```
GET  /api/person/[id]/roster/[period-id]
     - Personal assignment list
     - Only accessible after period PUBLISHED
     - Shows assignments + saldo impact
     - Response: { success, data: { assignments, saldo, period } }

GET  /api/person/[id]/notifications
     - List notifications (unread first)
     - Query: ?period_id=..., ?type=...
     - Response: { success, data: { notifications } }

POST /api/person/[id]/notifications/[notification-id]/read
     - Mark notification as read
     - Response: { success }

POST /api/person/[id]/swap-requests
     - Create swap request
     - Body: { period_id, offered_slot_id, requested_slot_id, notes? }
     - Validates: requester has offered_slot, respondent has requested_slot
     - Creates notification for respondent
     - Response: { success, data: { swap_request } }

GET  /api/person/[id]/swap-requests?period_id=...
     - List swap requests (as requester or respondent)
     - Response: { success, data: { requests: [] } }

POST /api/person/[id]/swap-requests/[request-id]/approve
     - Approve swap request
     - Body: { respondent_id }
     - Creates new assignments, archives old ones
     - Sends notification to requester
     - Response: { success, data: { assignments } }

POST /api/person/[id]/swap-requests/[request-id]/reject
     - Reject swap request
     - Body: { reason? }
     - Sends notification to requester
     - Response: { success }
```

## Validation Rules (Phase 3)

### Manual Assignment Constraints
1. **No duplicate assignments** - one person, one slot max
2. **Blocking respect** - cannot assign to ABSOLUUT slots
3. **Band compliance** - total assignments stay within band+delta range
4. **Window rule** - no consecutive within windowWeeks
5. **Part-time patterns** - forced assignments still respected

### Swap Request Validation
1. **Both slots exist** - offered and requested slots must exist
2. **Slot ownership** - requester owns offered, respondent owns requested
3. **Slot type compatibility** - both must be same shift_type (AVOND/WEEKEND/FEESTDAG)
4. **No conflicts** - swapping doesn't violate constraints for either person
5. **State check** - period must still allow swaps (not yet published)

### Publication Validation
1. **All slots filled** - no empty slots (capacity check)
2. **No hard violations** - zero ABSOLUUT blocking violations
3. **Band compliance** - all persons in band range
4. **Window rule** - no consecutive assignments
5. **Part-time forced** - all part-time patterns satisfied
6. **Audit trail** - no uncommitted edits
